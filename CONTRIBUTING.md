# Contributing to VulnLens

Thanks for helping make VulnLens better. This guide covers the setup,
workflow and rules that are specific to this repo — please read it before
opening a pull request.

## What VulnLens is

VulnLens X-rays a Maven project's supply chain against the live
[OSV.dev](https://osv.dev) vulnerability database. Point it at a `pom.xml`
(or a project directory) and it reports a risk score, a severity heatmap, a
sortable CVE table and a per-dependency upgrade suggestion. It is a
**zero-dependency Java CLI**: the shipped jar is pure `javac` output, no
Maven/Gradle build, no third-party libraries at runtime.

## Prerequisites

- Java 17+ (built and tested with Java 21)
- `bash` (the build script) and a Unix-like shell
- Network access to `https://api.osv.dev` at **scan time** — the tool queries
  OSV.dev live. The test suite does **not** need the network: it runs against
  real OSV.dev records stored as fixtures under `src/test/resources`.

## Build, test, run

```bash
./build.sh
```

That one command does everything, in order:

1. Fetches the JUnit 5 test dependencies into `lib/` (`tools/fetch-test-deps.sh`).
2. Compiles all sources under `src/main/java` with plain `javac`.
3. Packages `build/vulnlens.jar` (entry point `dev.vulnlens.VulnLens`).
4. Compiles and runs the JUnit 5 suite (currently 5.11.4) — the build
   **fails loudly on any test failure**, so a green `./build.sh` is the
   bar for every PR.
5. Regenerates `docs/sample-report.html` from `examples/vulnerable-sample/pom.xml`.

Try it out:

```bash
# scan the bundled example (six genuinely vulnerable-era dependencies)
java -jar build/vulnlens.jar examples/vulnerable-sample/pom.xml

# machine-readable output
java -jar build/vulnlens.jar pom.xml --format json --output report.json

# CI gate: exit 1 if anything at/above HIGH is found
java -jar build/vulnlens.jar pom.xml --fail-on high
```

## Exit codes

| Code | Meaning |
|------|---------|
| 0 | scan completed (report written) |
| 1 | `--fail-on <level>` threshold hit — something at/above that severity found |
| 2 | bad input (missing/malformed pom, bad flags) |
| 3 | OSV.dev unreachable (network down, API issues) |

Keep these stable: scripts and CI gates depend on them. If a change alters
an exit code, say so explicitly in the PR description.

## Project layout

```
src/main/java/dev/vulnlens/   # the app (zero dependencies)
  VulnLens.java               # CLI entry (exit-code contract above)
  cli/                        # argument parsing
  model/                      # Dependency, VulnRecord, Severity, ScanResult
  parse/                      # hand-rolled JSON parser, pom parser, Maven version ordering
  ...                         # scoring, OSV client, report renderers
src/test/java/                # JUnit 5 tests
src/test/resources/           # real OSV.dev records used as test fixtures
src/buildtools/               # helpers used by the build itself
tools/                        # fetch-test-deps.sh, gen-sample-report.sh
examples/vulnerable-sample/   # pom.xml pinning six vulnerable-era dependencies
docs/sample-report.html       # GENERATED — see below, never hand-edit
build.sh                      # the whole build: compile, test, package, regenerate docs
```

## Rules of the codebase

- **Zero dependencies.** Only the JDK standard library (including
  `javax.xml` for the XXE-hardened pom parser) is allowed at runtime. Do
  not add a library without discussing it in an issue first.
- **Never hand-edit `docs/sample-report.html`.** It is regenerated by
  `./build.sh` on every build. If the sample report looks wrong, fix the
  renderer or the example pom, then rebuild.
- **Never invent vulnerability data in tests.** Test fixtures are real
  OSV.dev records (see `src/test/resources`). If you need a new fixture,
  capture a real OSV response and note its source in the PR.
- **Keep the scoring formula honest.** Risk score = 25×critical + 10×high
  + 4×medium + 1×low, capped at 100 (grades: 0–19 Low, 20–39 Moderate,
  40–69 High, 70+ Critical). Severity "unknown" findings are listed but
  contribute nothing. Any change to the formula must update the README
  and the tests together.
- **Fix suggestions stay on the nearest release line.** A suggested fix is
  the smallest fixed version above the current one, maximised across the
  dependency's vulns so one upgrade fixes everything (2.3.24 → 2.3.35,
  not 2.5.17).
- **Scope: Maven only, direct dependencies only.** Gradle, npm, PyPI and
  transitive resolution are out of scope unless an issue explicitly
  re-opens them — say so in the PR if you touch that boundary.
- **An unreachable API is a clean error, not a guess.** Never silently
  fall back to stale or fabricated data; exit code 3 exists for this.

## Pull request workflow

1. Fork the repo and create a feature branch from `main`
   (`git checkout -b fix/short-description`).
2. Make one focused change per PR — a fix, a feature, or a docs update,
   not all three.
3. Add or update tests for behaviour changes, and run the full gate:
   `./build.sh` must pass end to end.
4. Update the README if flags, exit codes, the scoring formula or the
   layout changed.
5. Open the PR against `main` with a short description: what changed, why,
   and how you verified it (paste the `./build.sh` result and an example
   scan if relevant).

## Reporting vulnerabilities in VulnLens itself

VulnLens scans other projects for CVEs; if you find a security issue in
VulnLens (for example in the pom parser or the report renderer), please
open an issue describing it — do not use a public PR to demonstrate an
exploit against the tool.
